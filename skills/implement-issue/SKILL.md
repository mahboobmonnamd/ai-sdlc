# Implement issue

## Invocation contract
`/implement-issue <Issue>`; exact issue number is mandatory. Use existing project repository; never infer the issue number.

## When to use
New `needs:implementation` work or an authorized partial implementation on the **same branch/candidate**.

## Do not use
Do not claim from labels alone, invent design choices, run another owner's branch, create duplicate PRs, weaken checks, perform unrelated cleanup, or push without Gate 2.

## Required context
Fresh issue and DoR, accepted requirements/decisions/plan revision (where required), dependencies, security controls, ownership/claim adapter, candidate inventory including closed-unmerged PRs, current code/tests and project CI policy. See `docs/WORKING-LOOP.md` for states and claim guarantees.

## ADR authority

Apply the ADR lifecycle in `docs/WORKING-LOOP.md`: an ADR is proposed until its PR merges into the authoritative branch; merge is acceptance. Treat merged ADR content as binding regardless of stale status text. No separate acceptance step or status edit. A standalone ADR PR, or an authorized combined ADR/implementation PR with a final resolved decision, can establish its own authority at merge; a separate dependent PR must wait for the external ADR merge and reconcile to its exact content. An accepted evaluation process is not a selected candidate or passed qualification.

## Provisional contract lane
AI-SDLC does not grant architecture or security authority. When consuming-project policy explicitly permits parallel implementation, a pending architecture/security review or unresolved normative choice does not by itself block reversible implementation. The owning issue must name each provisional contract, the accepted baseline and revisions, selected interim value, unresolved alternatives and decision owner, affected surfaces, rollback/replacement path, tests, fail-closed/disabled behavior, and an explicit acceptance-before-merge gate.

Proceed only on parts whose boundary and failure behavior are testable. Never contradict accepted authority, expose an unreviewed permission or privacy path, make an irreversible migration, silently truncate or lose user data, or enable a capability whose safety depends on the unresolved decision. Isolate dependent behavior behind a tested boundary and keep it disabled; continue independent work. Mark code, evidence and PR claims as provisional. Implementation and independent architecture/security review may run concurrently.

A provisional candidate may be published and technically reviewed, but it is never merge-ready while a required choice remains unresolved or an external ADR prerequisite is unmerged. A final ADR reviewed in the same PR is not an external prerequisite. Before merge, resolve every recorded decision through the consumer's authority process, reconcile the implementation and tests against the accepted result, rerun affected checks, and obtain required exact-head review. Technical PR approval does not accept an ADR/specification before merge; the authorized ADR merge is acceptance. Packaging, distribution signing, and production qualification are separate gates; require them before implementation only when governing project authority explicitly says the source change itself requires them.

## Stop or escalate when
Other owner/candidate, unclear or rejected stage, material unsatisfied DoR/dependency/authority that is not explicitly and safely provisional, missing atomic claim for new work, mandatory tests failing/unavailable, or approval tied to a changed governing snapshot. If only a separable contract decision is unresolved, record it as provisional, block/disable dependent behavior, and continue independent accepted work.

## Desktop-safe testing

Before executing or delegating any test/check/benchmark (including retries), apply `docs/WORKING-LOOP.md#desktop-safe-test-execution`: inspect transitive desktop effects; prefer non-disruptive tests; resolve unknown effects by read-only inspection or verified containment; disruptive runs require a verified isolated runner or explicit per-run human authorization for a known bounded scope if consumer policy permits. Never self-authorize or bypass the consumer guard. Coordinate required headed suites with the convergence ledger; reuse only independently verified unaffected evidence, never prior desktop permission; rerun affected and mandatory exact-head checks safely. No duplicate specialist runs, unapproved retries or automatic review/fix recursion on blocked evidence. Continue separable safe work; unavailable mandatory evidence stays NOT_RUN / INCONCLUSIVE and blocks approval/merge. Escalate per canonical convergence policy.

## Procedure
1. **Read-only preflight:** fetch issue and its revision, candidate/branch links including closed-unmerged and merged content, claims, open concerns, dependent work and trusted sources. Determine NEW vs RESUME. If IN_REVIEW route to `process-review` for feedback; if UNKNOWN or duplicate owners/candidates stop. If work is partially implemented and owned, keep it in this skill even when CI/early feedback exists.
2. **Ready + plan:** assess all 12 DoR checks (verification command optional). Validate the existing 3–7-step plan against actual code seams, tests, dependencies, risks, rollback/compatibility and accepted architecture. Map AC → intended test; avoid a second plan-acceptance ceremony. Apply `docs/WORKING-LOOP.md#review-convergence-and-evidence-reuse`: independent read-only plan challenge for high-risk/material multi-component work, routine author plan validation otherwise unless consumer policy requires more; record findings in existing Gate 1 and resolve material gaps before edits. If project policy requires a separate approved plan, load its **exact accepted revision**. Do not silently alter decisions; refer gaps to `create-issue`.
3. **Gate 1:** show readiness table (collapsed passes allowed), proposed files/steps, tests, material risks and exact issue/plan revision. A direct user instruction that explicitly authorizes implementation of this issue and scope satisfies Gate 1; do not ask again. Otherwise ask **"Proceed with implementation? (yes/no)"**. On no stop without ownership claim, branch or edits. For an unchanged previously approved resume, reuse the saved approval; otherwise show material delta and re-ask.
4. **Claim:** after yes, re-fetch issue/decisions/dependencies. Set `PHASE=implement`, `NUMBER=<issue number>` and invoke `python3 "$AI_SDLC_TOOL_ROOT/tools/workflow_claims.py" begin --repo "$REPO" --phase implement --number "$NUMBER" --token-file "$AI_SDLC_CLAIM_TOKEN_FILE"` using the **host-configured** common `AI_SDLC_CLAIM_DB` and stable `AI_SDLC_WORKER_ID` (see `docs/WORKING-LOOP.md`). Only `ACQUIRED` or `RESUMED` permits continuing. Invoke the same command with `verify` (rather than `begin`) and require `VERIFIED` before the issue-label transition, branch/edit, push and PR publication. An atomically acquired claim must be `VERIFIED` before changing `needs:implementation` to `issue:implementing`. `BUSY`/`DENIED`/`ERROR` prevents those writes; report the owner when available, never fall back to labels or replace the candidate. A same-worker resume reuses its existing private token file without acquiring a second claim.
5. **Branch:** NEW → fetch `origin/main` and branch from its exact SHA (unless explicit authorized stack/dependency policy selects another base); RESUME → existing authorized head, including reopenable closed-unmerged PR. Never create a replacement merely because work spans sessions. Persist candidate stage `IMPLEMENTATION_IN_PROGRESS`.
6. **Implement with feedback:** write the smallest coherent production-intent code and tests; use a failing test when useful. After each root cause, run narrow checks. Include relevant negative, boundary/security, migration/recovery, concurrency, compatibility and integration coverage proportional to actual risk. Keep provisional behavior isolated, fail-closed and disabled; do not merge it while its choice is unresolved or its external ADR prerequisite is unmerged. Unrelated findings become separate issues, not changes in this PR.
7. **Verification:** run required project checks and risk-driven evidence on the finished candidate. Record exact local revision, commands/results and every criterion PASS/FAIL/INCONCLUSIVE, including each provisional decision and its remaining merge gate. Pre-PR self-review the entire diff for scope, test weakening, missing failure paths, API/docs claims and secret exposure. An unrun mandatory check is not passing; do not offer Gate 2 while mandatory evidence is failing. If the consumer requires developer-owned independent preflight, use the canonical convergence ledger, initial full review, batched fixes, focused rechecks and final independent exact-head whole-candidate review before readiness. Stop and escalate after 3 routine remediation cycles or earlier triggers; no new automatic budget at formal review. Keep formal review separate and no self-approval. Do not launch repeated full reviews on unfinished code or missing mandatory evidence.
8. **Gate 2:** display branch/base/head, diffstat, full acceptance→evidence matrix, check results, residual risks and **complete PR title/body** (`Closes #N`, summary, test proof, limits). Ask **"Push branch and create PR? (yes/no)"**; no push/PR on no. Previously approved unchanged candidate may resume without another prompt.
9. **Publish:** re-verify the *same* executable claim and approved issue scope, diff/head and base. Push exactly that branch; create or reuse one non-draft PR; apply PR `needs:review`, persist `IN_REVIEW`, mark issue `issue:in-review` (or project equivalent). Only after these writes and a confirmed handoff, invoke `python3 "$AI_SDLC_TOOL_ROOT/tools/workflow_claims.py" release --repo "$REPO" --phase implement --number "$NUMBER" --token-file "$AI_SDLC_CLAIM_TOKEN_FILE"`. A failed handoff retains the same claim/token for continuation; do not abandon the lock silently or create another PR. Record link and actual remote head. CI can run after push: report pending/failing remote status honestly. Label provisional decisions and link the required authority review; a pending decision keeps the PR blocked from merge. Never automatically approve or merge.

## Output contract
Mode NEW/RESUME; issue/current revision; candidate/stage/owner; DoR + validated plan; both gate decisions; exact branch/base/head; changed files/diffstat; AC→evidence table with commands and results; risks/unknowns; PR body/URL, remote CI and next action. Distinguish NOT_RUN from PASS.

## Handoff
PR opened → `pr-review` once evidence is available. Existing unfinished scope → resume `implement-issue`. Reviewed feedback → `process-review`. DoR or accepted authority gap → `create-issue` or decision owner. No duplicate candidate creation.
